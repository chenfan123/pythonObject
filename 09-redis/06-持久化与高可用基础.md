# 持久化与高可用基础

理解 Redis 的数据为什么不会因重启全部丢失，并能区分 RDB 与 AOF 的取舍。

持久化就是把内存状态保存到磁盘，以便重启后恢复。

## RDB：快照

RDB 定期把某个时刻的全部数据拍成一份快照文件。

```shell
save 3600 1
# 表示 3600 秒内只要有至少 1 次写入，就可以触发一次快照；其余两项是更高频写入时更积极地保存快照。
```

缺点：2 次快照之间的新写入不在最新快照中；Redis 在下一次快照前崩溃，可能丢失这段时间的数据。

## AOF：追加日志

AOF 不保存“某时刻的全量对象”，而是持续记录写命令。

Redis 重启时重放这些写操作，恢复数据。

```shell
# 当前配置
appendonly = yes
appendfsync = everysec
```

- everysec 表示 Redis 大约每秒将 AOF 刷到磁盘一次。性能与安全性比较平衡；极端故障下通常可能丢失最近约 1 秒的写入。

## AOF 刷盘策略的取舍

AOF 的关键配置是 `appendfsync`，决定「写命令进 AOF 后，多快真正落到磁盘」。

**`always`**

- 含义：每次写入都尽力刷磁盘
- 优点：数据丢失风险最低
- 代价：写性能最差

**`everysec`**

- 含义：大约每秒刷一次
- 优点：性能与可靠性平衡
- 代价：极端故障可能丢最近约 1 秒

**`no`**

- 含义：交给操作系统决定何时刷盘
- 优点：写入最快
- 代价：数据丢失窗口最大

> 当前环境的 `everysec` 是许多普通业务的常见平衡选择。

## 持久化和高可用解决不同问题

- 持久化：实例重启后，数据能否恢复？
- 高可用：实例故障时，服务能否尽快继续？
- 最基础的结构是主从复制：

```shell
应用
  ↓ 写
Primary（主 Redis）
  ├── Replica 1（副本）
  └── Replica 2（副本）
```

- 写请求通常进入 Primary。
- Primary 将写入变化复制给 Replica。
- Replica 可以承担部分只读流量，或在主节点故障时作为候选接管者。

但还需要“谁来发现 Primary 挂了、谁来切换”的组件，这就是 Sentinel：

```shell
Sentinel 集群发现 Primary 故障
→ 从 Replica 中选一个提升为新 Primary
→ 通知客户端新地址
→ 应用重新连接
```

Redis 复制通常是异步的。
