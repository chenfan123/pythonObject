### Worker 模型

- 请求压力：瞬间很多人访问接口
- 任务压力：单个任务很慢、很重、需要可靠完成

API worker 擅长处理请求压力.

Worker 模型把“接收任务”和“执行任务”拆开，队列的价值不是让任务凭空更快，而是削峰填谷。

Worker 模型的本质是：把慢任务隔离出来，并让系统能够明确控制“接收多少、同时处理多少、失败后如何恢复”。

可靠 Worker 需要“租约 / 心跳”,即 持有者崩溃时，资源不能被永久占住：

接受任务会重复、Worker 会崩溃；通过租约恢复卡死任务，通过幂等让重复执行无害。

```shell
Worker A 领取任务时：
- 写入 worker_id
- 写入 lease_expires_at，例如 5 分钟后
- 状态改为 processing

Worker A 仍在工作：
- 周期性续租 / 更新 heartbeat

其他 Worker 或调度器发现：
- processing，但 lease 已过期
→ 判定原 Worker 可能已死
→ 重新放回 queued，允许其他 Worker 领取
```

### 数据库和 HTTP 连接池

```shell
应用启动
→ 创建一个全局 AsyncEngine
→ Engine 内部维护连接池

每个请求
→ 创建自己的 AsyncSession
→ Session 从池中借一条连接
→ 执行 SQL、提交或回滚
→ Session 关闭，连接归还池中
```

- Engine / 连接池：应用级共享
- AsyncSession：请求级或任务级，不可跨并发请求共享
- Connection：需要时从池借，用完归还

连接池的真正作用不是提高数据库算力，而是：

- 复用连接，减少建连成本；
- 给单个进程设置资源上限；
- 池满时让请求等待或失败，形成保护边界。

应先排查的常见原因是：

- 慢 SQL / 缺索引
- 事务时间过长
- 连接未释放（Session 没有关闭）
- 下游数据库已过载
- Worker 并发过高
- 连接池与进程数乘积超过数据库承载

优化顺序通常是：

1. 修慢 SQL、缩短事务
2. 确保 Session 生命周期正确，连接能归还
3. 限制 API / Worker 并发
4. 根据数据库容量合理调连接池
5. 再考虑读写拆分、缓存或扩容

```python
@asynccontextmanager
async def lifespan(app: FastAPI):
    app.state.model_client = httpx.AsyncClient(
        timeout=httpx.Timeout(20.0),
        limits=httpx.Limits(
            max_connections=50,
            max_keepalive_connections=20,
        ),
    )
    try:
        yield
    finally:
        await app.state.model_client.aclose()
```

### 限流与背压

- 限流：限制“在一段时间内允许多少请求进入”
- 背压：处理不过来时，让上游放慢、等待或被拒绝

#### 限流

它主要保护的是：

- 公平性：单个用户不能占满资源；
- 成本：限制 LLM、Embedding 等按量计费调用；
- 安全：降低暴力登录、接口滥用；
- 下游：避免瞬间大量请求打进数据库或模型服务。

#### 背压

背压则是系统已经知道自己的处理能力有限，队列会持续增长。背压要求系统明确反馈“我已经处理不过来”，而不是无限接收。

- 队列低于阈值 → 接受任务，202
- 队列接近满 → 降级，例如延迟非关键任务
- 队列已满 → 拒绝新任务，429 或 503

固定窗口：
每个 60 秒重新计数
实现简单、成本低
缺点：窗口边界可能突刺

滑动窗口：
始终查看“最近 60 秒”
更平滑、更严格
缺点：需要记录更多时间戳，Redis 成本更高

令牌桶：（API 网关和高并发接口）
桶容量：10 个令牌
补充速度：每秒 1 个令牌
请求到来：拿走 1 个令牌才能通过

选择时不要死记算法：
场景 常见选择
简单后台接口、成本低优先 固定窗口
登录、发送验证码等边界敏感接口 滑动窗口
希望允许小幅突发、但控制长期平均速率 令牌桶
Worker 消费能力不足 队列上限 + 背压，不只是用户限流

- 限流：控制“谁、在多长时间内、能进来多少次”
- 背压：控制“系统现在还能接住多少工作”
- 令牌桶：允许短突发，控制长期平均速率
- 快速失败：宁可明确 429 / 503，也不要让请求无限堆积

### 超时与重试

超时不等于失败已确定；重试不等于一定安全。

超时链路通常应“由内到外逐渐放宽”：
Redis：很短
数据库：短
模型 HTTP：较长
API 网关：比内部调用再稍长一些
客户端：最长

重试还需要三个边界：次数、总时间预算、触发条件。

重试逻辑通常放在真正了解失败类型的调用边界：

- 调用 LLM / Embedding 的 Client 或 Service：知道哪些网络错误可重试
- Repository：只处理数据库操作和特定可恢复数据库错误
- Router：负责把最终领域结果转为 HTTP 响应

- 事务冲突 → 回滚整个事务 → 从头有限重试
- 网络暂态 → 在合适边界有限重试
- 业务确定错误 → 不重试
- 有副作用写操作 → 幂等后才谈重试

### 指数退避与抖动

指数退避（exponential backoff）的思路是：失败次数越多，等待越久。
抖动（jitter）：在等待时间上加入随机性。
