- 缓存穿透：请求的数据根本不存在
- 缓存击穿：热点真实数据过期，多个请求同时回源
- 缓存雪崩：大量 Key 在相近时间同时失效

# 缓存穿透

请求不存在的数据，缓存和数据源都没有结果，但每次请求仍打到数据源

缓存穿透 ≠ 缓存击穿 ≠ 缓存雪崩

缓存穿透：请求的数据根本不存在 → Cache miss → 数据源也找不到 → 下次请求仍重复访问数据源

> 例如：用户请求不存在的用户 ID，缓存和数据库都没有结果，但每次请求仍重复访问数据库。

解决方案（穿透）：

- 空值缓存：查不到也缓存空标记，短 TTL，避免反复打库
- 布隆过滤器：先拦截「肯定不存在」的请求

## 空值缓存

空值缓存解决的是“确实不存在的 Key 被反复访问”；

数据源查不到时，也往缓存写一个「空标记」，并设很短 TTL。

下次同样请求会命中空值，不再打数据库；短 TTL 避免「后来新建了数据却一直读到空」。

```
SET cache:user:1001 "null" EX 60
```

代价：缓存里会多很多空 key；恶意扫号仍可能把缓存打满，通常要配合限流或布隆过滤器。

## 布隆过滤器

布隆过滤器不保存完整 ID，而是保存多个哈希后的 bit 标记。

用很小的空间记住「哪些 id 可能存在」。请求先问布隆过滤器：

- 明确不存在 → 直接拒绝，不查缓存、不查库
- 可能存在 → 再走正常 Cache Aside

特点：

- 有误判：可能把「不存在」判成「可能存在」（假阳性），极少把「存在」判成「不存在」
- 适合拦截大量非法 / 乱猜 id，降低穿透流量
- Redis 常用 RedisBloom 模块（`BF.ADD` / `BF.EXISTS`），不要用普通 `SADD` 集合冒充——Set 能去重，但内存和误判模型都不同

## 互斥锁 / 单飞

→ 只有一个请求重建缓存
→ 其他请求等待或稍后重试

实现原理：多个请求到来时，其中一个请求设置锁`SET lock:key token NX EX 5`，其他请求如果 set 锁会失败，因为 NX 表示如果锁不存在，则设置锁，所以就会轮训一定间隔查询缓存。那个设置锁的请求查到数据源之后，然后重新设置缓存。

- NX：如果锁不存在，则设置锁
- EX 5：锁的过期时间
- token：锁的唯一标识

## 逻辑过期

缓存中存储过期时间，在过期时间之前，如果发现缓存过期了，则再查一次数据源。
需要代码层面上锁，多次请求只有 1 个实际去更新了，其他的直接拿缓存。

# 缓存雪崩

大量不同 Key 同时失效。

常见防护：

1. TTL 加随机抖动
2. 热点 Key 使用互斥重建
3. 数据库连接池、限流、降级兜底
4. Redis 高可用，避免 Redis 整体不可用

## Redis 不可用时，如何保护数据库

降级策略：
有可用旧副本：返回短暂陈旧的商品详情；
没有旧副本：返回简化信息或“服务繁忙，请稍后重试”；
同时限制真正回源数据库的请求数量。

随机抽取能削峰，但若要体验更稳定，常用固定规则（例如按用户标识做稳定分流）或明确的限流队列
