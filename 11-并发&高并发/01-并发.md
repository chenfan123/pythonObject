##### 适合 to_thread 的典型条件：

- 通常几百毫秒到几秒内完成；
- 调用者必须立刻拿到结果；
- 失败直接返回本次接口错误即可；
- 没有复杂的重试、进度、断点续跑需求。

##### 适合独立 Worker 的典型条件：

- 可能运行几十秒、几分钟，甚至更久；
- CPU/GPU 或内存占用明显；
- 需要排队、限制并发、重试、任务状态；
- 服务重启后仍希望任务可恢复；
- 例如文档导入、批量生成 Embedding、知识库重建、批量调用模型。

CPU / 内存重活：不要堵在 Web API 进程
同步 I/O：优先异步客户端；暂时只能同步时用 to_thread
长流程：任务表 + 队列 + Worker
关键任务投递：数据库事务(却保入库与投递的原子性) + Outbox

> Worker 通常要有并发上限。`semaphore = asyncio.Semaphore(2)`Semaphore(2) 不是让解析更快，而是保护系统：任何时刻最多两项重活运行；剩下的等待或留在消息队列中。

- Semaphore：进程内并发保护
- Redis / DB：跨进程、跨机器的全局协调
- TTL / 租约：避免崩溃后资源永久被占

### 进程池

进程池解决的是：一台机器上，怎么把 CPU 计算分配到多个进程。

```python
from concurrent.futures import ProcessPoolExecutor
import asyncio

pool = ProcessPoolExecutor(max_workers=2) # 创建一个进程池，最大并发数为2

async def extract_text(file_path: str) -> str:
    loop = asyncio.get_running_loop() # 获取当前事件循环
    return await loop.run_in_executor(pool, parse_pdf, file_path) # 在进程池中执行同步函数
```

### 任务队列

任务队列解决的是：任务如何脱离 HTTP 请求、可靠排队、被多台机器上的 Worker 获取并执行。

### 总结

- 队列：决定“哪个任务该被处理”
- Worker：负责取任务和更新状态
- 进程池：Worker 内部执行 CPU 密集步骤的工具
- Redis / DB：协调状态、限流、幂等、分布式锁

## 并发下的共享状态与竞态条件

并发问题不在于“同时执行”，而在于多个执行者对同一份可变状态，做了非原子的“读 → 判断 → 写”。

- Python 可变默认参数共享：意外共享状态
- asyncio.Lock：进程内状态保护
- Redis 原子操作：分布式短期协调
- PostgreSQL 事务 / 行锁 / 条件更新：业务事实一致性

对于支付、创建订单、发券、任务创建等“重复执行有副作用”的写操作，常见组合是：

```shell
客户端携带 Idempotency-Key: pay-abc-123

服务端首次处理：
  记录 key = pay-abc-123，绑定订单/支付结果
  执行业务

同 key 重试：
  不重复扣款
  直接返回第一次的结果，或告知处理中


幂等键 + 数据库 UNIQUE 约束
        ↓
防止重复请求产生多份业务结果

事务 / 条件更新 / 行锁
        ↓
保证同一份业务事实在并发修改时一致

Outbox
        ↓
保证数据库提交后的异步事件能可靠投递
```

## 协程并发控制工具

- Lock：同一时刻只能一个人修改某份共享状态
- Semaphore：同一时刻最多 N 人做某类工作
- Queue：任务先排队，由消费者按能力逐个/有限并发处理
- 任务状态表：记录跨重启仍存在的业务进度
- 幂等机制：接受消息或任务可能被重复处理

#### asyncio.Lock：保护临界区

```python
lock = asyncio.Lock()
balance = 100

async def withdraw(amount: int):
    global balance

    async with lock:
        if balance < amount:
            return False

        await asyncio.sleep(0)  # 模拟中途可切换
        balance -= amount
        return True
```

async with lock 包住的是“读余额 → 判断 → 写余额”这个整体。若只锁写入，读取和判断仍可能基于旧值，问题还在。

但它只适合单进程内的 balance 这种临时状态；数据库余额要让数据库自己保护。

#### asyncio.Semaphore(n)：控制并发容量

```python
embedding_limit = asyncio.Semaphore(5)

async def create_embedding(text: str):
    async with embedding_limit:
        return await embedding_client.embed(text)
```

#### asyncio.Queue：生产者与消费者解耦

```python
queue: asyncio.Queue[str] = asyncio.Queue()

async def producer(task_id: str):
    await queue.put(task_id)

async def worker():
    while True:
        task_id = await queue.get()
        try:
            await process(task_id)
        finally:
            queue.task_done()
```

解决的是“任务来得比处理能力快”.

多个 Worker 同时消费同一队列时，队列会把不同任务分发给不同消费者；不是每个 Worker 都处理每个任务。

背压：若生产速度持续大于消费速度,队列会无限增长，最后占满内存。给本地队列设上限,当队列已有 上限项 时，会等待，直到有消费者取走一个任务。

## 任务编排、超时与异常传播

目标是避免两个问题：

- 一个子任务失败，其他任务仍在后台继续跑
- 一个远程调用卡很久，HTTP 请求一直占着资源

2 个工具：

- await coroutine：当前流程等待它完成。`profile = await fetch_profile(user_id)`
- asyncio.create_task(...)：把协程注册为独立 Task，允许它与当前协程并发运行。`profile_task = asyncio.create_task(fetch_profile(user_id))`

当多个子任务必须都成功，Python 3.11+ 推荐 TaskGroup：

```python
async with asyncio.TaskGroup() as group:
    profile_task = group.create_task(fetch_profile(user_id))
    settings_task = group.create_task(fetch_settings(user_id))

profile = profile_task.result()
settings = settings_task.result()

# 其中一个任务抛异常
# → TaskGroup 取消其余尚未完成的兄弟任务
# → 等待清理完成
# → 向外传播异常
```

```shell
gather：
A 失败 → 外层收到异常
B 可能仍继续执行

TaskGroup：
A 失败 → 取消 B
       → 等 B 清理
       → 外层收到异常
```

- 子任务必须“同生共死”时，用 TaskGroup；
- 希望收集多个相互独立任务的成功/失败结果时，可使用 gather(..., return_exceptions=True)。return_exceptions=True 不是“异常消失”，而是把异常对象放入结果列表，由你显式处理

```python
answer = await asyncio.wait_for(
    llm_client.chat(prompt),
    timeout=15,
)
```

超过 15 秒时，wait_for 会尝试取消内部协程，并向外抛 TimeoutError。路由层或全局异常处理可将其映射成合适的 HTTP 响应，例如依赖服务超时常用 504。

- 独立 I/O，且都必须成功 → TaskGroup
- 批量任务，允许部分失败 → gather(return_exceptions=True)
- 单个外部调用需要时限 → wait_for / 客户端 timeout
- 可靠长任务 → 队列 Worker，不依赖 create_task

- create_task：启动并发任务
- TaskGroup：一项失败，取消其余，适合整体结果
- gather：适合汇总；允许部分失败时显式处理异常
- wait_for：限制等待时间
- 取消 / 超时：不等于远端动作一定没发生
- 幂等与状态记录：保证重试不会制造重复副作用

## 并发对象的边界——哪些能共享，哪些绝不能共享

避免一种很隐蔽的问题：代码看起来是异步的，但多个协程共用一个“带状态的对象”，导致事务串线、连接冲突或数据错乱。

AsyncSession 是一次工作单元，不是全局并发安全的数据库客户端。

不要把 API 请求的 Session 传给后台 Worker。HTTP 请求结束时 Session 应关闭，而 Worker 是独立的执行生命周期。

```shell
可以应用级复用的对象：
AsyncEngine / 数据库连接池
httpx.AsyncClient
Redis 异步客户端（连接池）
模型 API 异步客户端
```

短 I/O → async/await
同步 I/O SDK → to_thread 作为兼容
CPU 重活 → 进程 / 独立 Worker
长任务 → 队列 + Worker + 任务状态
进程内限制 → Semaphore
跨实例限制 → Redis / DB
最终业务事实 → 数据库事务、约束、原子更新
重复请求 / 重复消费 → 幂等'
